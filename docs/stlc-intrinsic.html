Dependent De Bruijn Indices and Intrinsic Typing

This is supplementary material and is not required reading for the course. It is intended for students who want to go deeper into the formal foundations.

Prerequisites: the STLC lecture and the type soundness notes.

In the type soundness notes, we proved progress and preservation for STLC the hard way. We defined untyped expressions, a separate typing relation, substitution with de Bruijn index arithmetic, a weakening lemma, a commutation lemma, and then proved progress and preservation. It was about 400 lines of Lean4, and the substitution infrastructure alone was 130 lines.

What if we could get the same guarantee with a fraction of the work?

The idea: instead of defining expressions and then proving they’re well-typed, we define expressions that are well-typed by construction. The de Bruijn indices become dependent: the term type is indexed by its typing context and its type. A Term Γ τ is, by construction, a well-typed term of type τ in context Γ. If you can build the term, it’s well-typed. If it’s ill-typed, you can’t build it.

This is sometimes called intrinsic typing, and it’s one of the deepest ideas in programming language theory. The principle extends far beyond type soundness: encoding invariants into your data structures eliminates the need to prove those invariants hold. Rust’s borrow checker, Haskell’s GADTs, and dependent types in Agda/Lean all use this idea.

What Changes?

In the extrinsic approach (the type soundness notes), we had two separate things:

-- The term (untyped data)
Expr : Type

-- The typing judgement (a separate proof)
HasType : Ctx → Expr → Ty → Prop

A term exists independently of its type. You construct the term, then separately prove it has a type. In the dependent de Bruijn approach, we fuse them:

-- The term IS the typing proof
Term : Ctx → Ty → Type

A Term Γ τ is simultaneously a term and a proof that it has type τ in context Γ. There’s no such thing as an ill-typed term.

QuickAnswer

In the extrinsic approach, what happens if you construct Expr.app (Expr.litInt 5) (Expr.litInt 3)? Is it well-typed? In the dependent de Bruijn approach, can you construct the analogous term?

The Full Lean4 Development

Types and contexts

Types are the same as before. A context is a list of types (de Bruijn: head is the most recent binder):

inductive Ty : Type where
  | int  : Ty
  | bool : Ty
  | arrow : Ty → Ty → Ty
  deriving DecidableEq, Repr

abbrev Ctx := List Ty

Variables as membership proofs

In the extrinsic version, a variable was a Nat (de Bruijn index) plus a separate proof that the context maps it to the right type. With dependent de Bruijn, the variable is the proof: Mem τ Γ is a constructive proof that type τ appears in context Γ.

inductive Mem : Ty → Ctx → Type where
  | here  : {Γ : Ctx} → {τ : Ty} → Mem τ (τ :: Γ)
  | there : {Γ : Ctx} → {τ σ : Ty} → Mem τ Γ → Mem τ (σ :: Γ)

Mem.here says “I’m variable 0 and my type matches the head of the context.” Mem.there m says “skip one binder and use proof m for the rest.” For example, in context [int, bool, int]:

  • Mem.here : variable 0 has type int
  • Mem.there Mem.here : variable 1 has type bool
  • Mem.there (Mem.there Mem.here) : variable 2 has type int

There’s no way to construct a Mem .bool [.int, .int]: bool isn’t in [int, int]. Out-of-scope and mistyped variable references are unrepresentable.

Intrinsically-typed terms

Each constructor enforces its typing rule. Compare with the extrinsic version side by side:

Extrinsic (HasType) 
| tLam (Γ : Ctx) (τ₁ τ₂ : Ty)
  (body : Expr)
  : HasType (Γ.extend τ₁) body τ₂
  → HasType Γ (.lam τ₁ body) (τ₁ ⇒ τ₂)
Dependent de Bruijn 
| lam : Term (τ₁ :: Γ) τ₂
      → Term Γ (τ₁ ⇒ τ₂)
Extrinsic (HasType) 
| tApp (Γ : Ctx) (e₁ e₂ : Expr)
  (τ₁ τ₂ : Ty)
  : HasType Γ e₁ (τ₁ ⇒ τ₂)
  → HasType Γ e₂ τ₁
  → HasType Γ (.app e₁ e₂) τ₂
Dependent de Bruijn 
| app : Term Γ (τ₁ ⇒ τ₂)
      → Term Γ τ₁
      → Term Γ τ₂

Look at app. The extrinsic version takes two expressions plus two typing proofs. The dependent version takes two typed terms: the function must have type τ₁ ⇒ τ₂ and the argument must have type τ₁. If you try to pass a Term Γ .bool as the function, Lean rejects it: .bool doesn’t unify with τ₁ ⇒ τ₂.

The full definition:

inductive Term : Ctx → Ty → Type where
  | var     : {Γ : Ctx} → {τ : Ty} → Mem τ Γ → Term Γ τ
  | litInt  : {Γ : Ctx} → Int → Term Γ .int
  | litBool : {Γ : Ctx} → Bool → Term Γ .bool
  | lam     : {Γ : Ctx} → {τ₁ τ₂ : Ty} → Term (τ₁ :: Γ) τ₂ → Term Γ (τ₁ ⇒ τ₂)
  | app     : {Γ : Ctx} → {τ₁ τ₂ : Ty} → Term Γ (τ₁ ⇒ τ₂) → Term Γ τ₁ → Term Γ τ₂
  | add     : {Γ : Ctx} → Term Γ .int → Term Γ .int → Term Γ .int
  | neg     : {Γ : Ctx} → Term Γ .int → Term Γ .int
  | ifz     : {Γ : Ctx} → {τ : Ty} → Term Γ .int → Term Γ τ → Term Γ τ → Term Γ τ
  | letE    : {Γ : Ctx} → {τ₁ τ₂ : Ty} → Term Γ τ₁ → Term (τ₁ :: Γ) τ₂ → Term Γ τ₂

inductive Value : {Γ : Ctx} → {τ : Ty} → Term Γ τ → Prop where
  | litInt  {Γ : Ctx} (n : Int)                                    : Value (Γ := Γ) (.litInt n)
  | litBool {Γ : Ctx} (b : Bool)                                   : Value (Γ := Γ) (.litBool b)
  | lam     {Γ : Ctx} {τ₁ τ₂ : Ty} (body : Term (τ₁ :: Γ) τ₂)   : Value (.lam body)

Renaming and weakening

In the extrinsic version, shifting (adjusting de Bruijn indices when moving under a binder) was a function on raw Nat indices, and we needed a weakening theorem (30+ lines) to show it preserved typing. With dependent de Bruijn, renaming is a typed function. A Ren Γ Δ maps variables in Γ to variables in Δ, preserving types. Weakening falls out as a one-liner:

abbrev Ren (Γ Δ : Ctx) := {τ : Ty} → Mem τ Γ → Mem τ Δ

def Ren.ext {Γ Δ : Ctx} {τ : Ty} (ρ : Ren Γ Δ) : Ren (τ :: Γ) (τ :: Δ) :=
  fun {σ} m => match m with
  | .here => .here
  | .there m' => .there (ρ m')

def rename {Γ Δ : Ctx} {τ : Ty} (ρ : Ren Γ Δ) : Term Γ τ → Term Δ τ
  | .var m        => .var (ρ m)
  | .litInt n     => .litInt n
  | .litBool b    => .litBool b
  | .lam body     => .lam (rename ρ.ext body)
  | .app e₁ e₂    => .app (rename ρ e₁) (rename ρ e₂)
  | .add e₁ e₂    => .add (rename ρ e₁) (rename ρ e₂)
  | .neg e        => .neg (rename ρ e)
  | .ifz e₁ e₂ e₃ => .ifz (rename ρ e₁) (rename ρ e₂) (rename ρ e₃)
  | .letE e₁ e₂   => .letE (rename ρ e₁) (rename ρ.ext e₂)

def weaken {Γ : Ctx} {τ σ : Ty} : Term Γ τ → Term (σ :: Γ) τ :=
  rename (fun m => .there m)

Compare weaken here (one line, no proof) with the 30-line weakening theorem in the extrinsic version.

Typed substitution

A Sub Γ Δ maps variables in Γ to terms in Δ. Again, the types are preserved by construction:

abbrev Sub (Γ Δ : Ctx) := {τ : Ty} → Mem τ Γ → Term Δ τ

def Sub.ext {Γ Δ : Ctx} {τ : Ty} (σs : Sub Γ Δ) : Sub (τ :: Γ) (τ :: Δ) :=
  fun {ρ} m => match m with
  | .here => .var .here
  | .there m' => weaken (σs m')

def subst {Γ Δ : Ctx} {τ : Ty} (σs : Sub Γ Δ) : Term Γ τ → Term Δ τ
  | .var m        => σs m
  | .litInt n     => .litInt n
  | .litBool b    => .litBool b
  | .lam body     => .lam (subst σs.ext body)
  | .app e₁ e₂    => .app (subst σs e₁) (subst σs e₂)
  | .add e₁ e₂    => .add (subst σs e₁) (subst σs e₂)
  | .neg e        => .neg (subst σs e)
  | .ifz e₁ e₂ e₃ => .ifz (subst σs e₁) (subst σs e₂) (subst σs e₃)
  | .letE e₁ e₂   => .letE (subst σs e₁) (subst σs.ext e₂)

def substSingle {Γ : Ctx} {τ₁ : Ty} (v : Term Γ τ₁) : Sub (τ₁ :: Γ) Γ :=
  fun {τ} m =>
    match τ, m with
    | _, .here     => v
    | _, .there m' => .var m'

def substTop {Γ : Ctx} {τ₁ τ₂ : Ty} (v : Term Γ τ₁) (body : Term (τ₁ :: Γ) τ₂) : Term Γ τ₂ :=
  subst (substSingle v) body

Look at substTop’s type: it takes v : Term Γ τ₁ and body : Term (τ₁ :: Γ) τ₂ and returns Term Γ τ₂. The substitution lemma from the extrinsic version (130 lines of proof) is now the type signature of a function. No commutation lemma, no insertAt, no generalization over position. The types do all the work.

QuickAnswer

Why doesn’t the dependent de Bruijn version need a commutation lemma (extend_insertAt) for substitution under binders?

Small-step semantics: preservation is the signature

The critical difference:

-- Extrinsic: preservation is a THEOREM
Step : Expr → Expr → Prop
preservation : HasType Γ e τ → Step e e' → HasType Γ e' τ  -- 40 lines

-- Dependent de Bruijn: preservation is the TYPE SIGNATURE
Step : Term Γ τ → Term Γ τ → Prop
-- Both sides have the same Γ and τ. Nothing to prove.

The full step relation:

inductive Step : {Γ : Ctx} → {τ : Ty} → Term Γ τ → Term Γ τ → Prop where
  | appL     {Γ : Ctx} {τ₁ τ₂ : Ty} {e₁ e₁' : Term Γ (τ₁ ⇒ τ₂)} {e₂ : Term Γ τ₁}
             : Step e₁ e₁' → Step (.app e₁ e₂) (.app e₁' e₂)
  | appR     {Γ : Ctx} {τ₁ τ₂ : Ty} {v₁ : Term Γ (τ₁ ⇒ τ₂)} {e₂ e₂' : Term Γ τ₁}
             : Value v₁ → Step e₂ e₂' → Step (.app v₁ e₂) (.app v₁ e₂')
  | appAbs   {Γ : Ctx} {τ₁ τ₂ : Ty} {body : Term (τ₁ :: Γ) τ₂} {v₂ : Term Γ τ₁}
             : Value v₂ → Step (.app (.lam body) v₂) (substTop v₂ body)
  | addL     {Γ : Ctx} {e₁ e₁' e₂ : Term Γ .int}
             : Step e₁ e₁' → Step (.add e₁ e₂) (.add e₁' e₂)
  | addR     {Γ : Ctx} {v₁ e₂ e₂' : Term Γ .int}
             : Value v₁ → Step e₂ e₂' → Step (.add v₁ e₂) (.add v₁ e₂')
  | addN     {Γ : Ctx} {n₁ n₂ : Int}
             : Step (.add (.litInt n₁) (.litInt n₂)) (.litInt (n₁ + n₂) : Term Γ .int)
  | negStep  {Γ : Ctx} {e e' : Term Γ .int}
             : Step e e' → Step (.neg e) (.neg e')
  | negN     {Γ : Ctx} {n : Int}
             : Step (.neg (.litInt n)) (.litInt (-n) : Term Γ .int)
  | ifStep   {Γ : Ctx} {τ : Ty} {e₁ e₁' : Term Γ .int} {e₂ e₃ : Term Γ τ}
             : Step e₁ e₁' → Step (.ifz e₁ e₂ e₃) (.ifz e₁' e₂ e₃)
  | ifTrue   {Γ : Ctx} {τ : Ty} {e₂ e₃ : Term Γ τ}
             : Step (.ifz (.litInt 0) e₂ e₃) e₂
  | ifFalse  {Γ : Ctx} {τ : Ty} {n : Int} {e₂ e₃ : Term Γ τ}
             : n ≠ 0 → Step (.ifz (.litInt n) e₂ e₃) e₃
  | letStep  {Γ : Ctx} {τ₁ τ₂ : Ty} {e₁ e₁' : Term Γ τ₁} {e₂ : Term (τ₁ :: Γ) τ₂}
             : Step e₁ e₁' → Step (.letE e₁ e₂) (.letE e₁' e₂)
  | letVal   {Γ : Ctx} {τ₁ τ₂ : Ty} {v₁ : Term Γ τ₁} {e₂ : Term (τ₁ :: Γ) τ₂}
             : Value v₁ → Step (.letE v₁ e₂) (substTop v₁ e₂)

Progress

Progress still needs a proof (it’s about behavior, not types), but canonical forms is gone. When e₁ : Term [] (τ₁ ⇒ τ₂) is a value, pattern matching on Value e₁ directly gives Value.lam body: no other value constructor produces an arrow type. The type index does the work that the canonical forms lemma used to do.

theorem progress {τ : Ty} (t : Term [] τ) :
    Value t ∨ ∃ t' : Term [] τ, Step t t' := by
  match t with
  | .var m => exact (nomatch m)
  | .litInt _  => left; exact Value.litInt _
  | .litBool _ => left; exact Value.litBool _
  | .lam _     => left; exact Value.lam _
  | .app e₁ e₂ =>
    right
    have ih₁ := progress e₁
    have ih₂ := progress e₂
    rcases ih₁ with hv₁ | ⟨e₁', hs₁⟩
    · rcases ih₂ with hv₂ | ⟨e₂', hs₂⟩
      · cases hv₁ with
        | lam body => exact ⟨_, Step.appAbs hv₂⟩
      · exact ⟨_, Step.appR hv₁ hs₂⟩
    · exact ⟨_, Step.appL hs₁⟩
  | .add e₁ e₂ =>
    right
    have ih₁ := progress e₁
    have ih₂ := progress e₂
    rcases ih₁ with hv₁ | ⟨e₁', hs₁⟩
    · rcases ih₂ with hv₂ | ⟨e₂', hs₂⟩
      · cases hv₁ with
        | litInt n₁ => cases hv₂ with
          | litInt n₂ => exact ⟨_, Step.addN⟩
      · exact ⟨_, Step.addR hv₁ hs₂⟩
    · exact ⟨_, Step.addL hs₁⟩
  | .neg e =>
    right
    have ih := progress e
    rcases ih with hv | ⟨e', hs⟩
    · cases hv with
      | litInt n => exact ⟨_, Step.negN⟩
    · exact ⟨_, Step.negStep hs⟩
  | .ifz e₁ e₂ e₃ =>
    right
    have ih₁ := progress e₁
    rcases ih₁ with hv₁ | ⟨e₁', hs₁⟩
    · cases hv₁ with
      | litInt n =>
        by_cases h : n = 0
        · subst h; exact ⟨_, Step.ifTrue⟩
        · exact ⟨_, Step.ifFalse h⟩
    · exact ⟨_, Step.ifStep hs₁⟩
  | .letE e₁ e₂ =>
    right
    have ih₁ := progress e₁
    rcases ih₁ with hv₁ | ⟨e₁', hs₁⟩
    · exact ⟨_, Step.letVal hv₁⟩
    · exact ⟨_, Step.letStep hs₁⟩

Notice: the .app case does cases hv₁ with | lam body => ... directly. No canonical forms lemma needed. The type index τ₁ ⇒ τ₂ forces the only possible value constructor to be lam.

Type soundness

Preservation is free. Type soundness is just progress applied after multi-step:

inductive MultiStep : {Γ : Ctx} → {τ : Ty} → Term Γ τ → Term Γ τ → Prop where
  | refl  {Γ : Ctx} {τ : Ty} {t : Term Γ τ} : MultiStep t t
  | step  {Γ : Ctx} {τ : Ty} {t t' t'' : Term Γ τ}
          : Step t t' → MultiStep t' t'' → MultiStep t t''

theorem type_soundness {τ : Ty} (t : Term [] τ) {t' : Term [] τ}
    (hms : MultiStep t t') :
    Value t' ∨ ∃ t'' : Term [] τ, Step t' t'' :=
  progress t'

That’s it. One line. Preservation doesn’t appear because it was never needed: Step already guarantees the type is preserved by its signature.

The Comparison

  Extrinsic Dependent de Bruijn
Terms Expr : Type (untyped) Term : Ctx → Ty → Type (typed)
Typing relation HasType (9-rule inductive) Built into Term
Variables Nat + lookup proof Mem τ Γ (proof IS the variable)
Preservation 40-line theorem Free (type signature)
Substitution lemma 130 lines Not needed (function is typed)
Weakening 30-line theorem One-line function
Canonical forms Separate lemma Pattern matching
Ill-typed terms Representable Unrepresentable
Total Lean4 LOC ~400 ~180

What we gained

Dependent de Bruijn cuts the formalization roughly in half. Preservation, the substitution lemma, weakening, and canonical forms all either vanish or become trivial. The code is shorter and carries more information.

What we lost

Terms are harder to construct: you need membership proofs for variables instead of raw numbers. Metaprograms that generate terms (compilers, for example) need to produce typed output, which can be more work. And the indexed type Term : Ctx → Ty → Type requires a type system (like Lean4’s) that supports indexed inductive families.

The deeper lesson

This isn’t just a proof technique. It’s a design principle: encoding invariants into your data structures eliminates entire categories of bugs. Rust’s ownership system prevents use-after-free not by checking at runtime, but by making dangling pointers unrepresentable in the type system. The same principle is at work here: we made ill-typed terms unrepresentable, and preservation became free.

When you design a system, ask: what invariants could I encode into the types? Every invariant you encode is an invariant you never have to check, test, or prove.
