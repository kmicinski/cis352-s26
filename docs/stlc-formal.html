Type Soundness for STLC

This is supplementary material and is not required reading for the course. It is intended for students who want to go deeper into the formal foundations.

Companion to the STLC lecture. Read that first.

In the STLC lecture, we claimed that well-typed programs don’t go wrong. In this lecture, we make that claim precise and prove it. The proof has two parts, progress and preservation, proved by induction over the typing derivation. We will also develop the proof in Lean4, a proof assistant where the computer checks every step of our reasoning.

The emphasis throughout is on why each step works, not just the formal mechanics. If you find yourself losing the forest for the trees, come back to this: type soundness says that evaluation never produces a nonsensical state. Progress says you’re never stuck. Preservation says you never drift off course.

What Does “Safe” Mean?

A term is stuck if it is not a value and cannot take a step. For example, (5 3) is stuck in the untyped λ-calculus: 5 is not a function, so we can’t β-reduce, and it’s not a value either. Stuck terms are the runtime type errors we want to prevent.

Type soundness says: if a term is well-typed, it never gets stuck. No matter how many steps of evaluation we take, we either reach a value or we can keep going.

This decomposes into two properties:

  • Progress: a well-typed closed term is either a value or can step. (“You can always make a move.”)

  • Preservation: if a well-typed term steps, the result is still well-typed at the same type. (“You stay on the right track.”)

Together: you can always make a move (progress), and each move keeps your type the same (preservation), so you never arrive at a stuck state with a bad type.

QuickAnswer

Give an example of a stuck term in the untyped λ-calculus. Why is it stuck? (Hint: try applying a non-function to something.)

Lean4 Definitions: Syntax, Typing, Semantics

Before the proofs, let’s see the full system in Lean4. Every definition here corresponds to something from the STLC lecture. Lean4 is a dependently-typed language: it can express propositions as types and proofs as programs. We define our STLC system as inductive data types, then prove properties about them using tactics.

Types

Types are int, bool, or function types τ₁ ⇒ τ₂:

inductive Ty : Type where
  | int  : Ty
  | bool : Ty
  | arrow : Ty → Ty → Ty
  deriving DecidableEq, Repr

De Bruijn indices: how variables work

In the STLC lecture, we used named variables: (λ (x : int) x). But names create headaches in formal proofs: we need α-equivalence, capture-avoiding substitution, and freshness conditions. De Bruijn indices eliminate all of this by replacing names with numbers.

The idea: a variable is a natural number that counts how many binders you have to skip over to reach the one that binds it. Variable 0 refers to the nearest enclosing binder, 1 to the next one out, and so on:

Named:       (λ (x : int) (λ (y : bool) x))
De Bruijn:   (λ int (λ bool (var 1)))
                                  ↑
                          skip 1 binder (past y) to reach x

Named:       (λ (x : int) (λ (y : bool) y))
De Bruijn:   (λ int (λ bool (var 0)))
                                  ↑
                          skip 0 binders: nearest binder is y

Named:       (λ (f : int → int) (λ (x : int) (f x)))
De Bruijn:   (λ (int ⇒ int) (λ int (app (var 1) (var 0))))
                                          ↑          ↑
                                      f = skip 1   x = skip 0

The payoff: two terms that differ only in variable names (α-equivalent terms) get the exact same de Bruijn representation. We never need to rename variables, and substitution becomes a mechanical operation on indices.

Write (λ (x : int) (λ (y : int) (+ x y))) in de Bruijn notation. What index does x get? What about y?

Expressions and values

inductive Expr : Type where
  | var     : Nat → Expr
  | litInt  : Int → Expr
  | litBool : Bool → Expr
  | lam     : Ty → Expr → Expr
  | app     : Expr → Expr → Expr
  | add     : Expr → Expr → Expr
  | neg     : Expr → Expr
  | ifz     : Expr → Expr → Expr → Expr
  | letE    : Expr → Expr → Expr
  deriving Repr

inductive Value : Expr → Prop where
  | litInt  (n : Int)              : Value (.litInt n)
  | litBool (b : Bool)             : Value (.litBool b)
  | lam     (τ : Ty) (body : Expr) : Value (.lam τ body)

A note on the .foo syntax in Lean4. You’ll see .litInt, .lam, .app, etc. throughout this code. The dot prefix is Lean4’s shorthand for a constructor when the type can be inferred from context. Writing .litInt n is short for Expr.litInt n: Lean knows from the surrounding type that we’re building an Expr, so we can drop the Expr. prefix and just write .litInt. Similarly, .int is short for Ty.int. You’ll see this everywhere in Lean4 code: it keeps things concise without losing information, because the type checker always knows which type’s constructor you mean. If you see .foo, mentally read it as “the foo constructor of whatever type is expected here.”

Value is a proposition: Value e is a type that is inhabited exactly when e is a literal or a lambda. The constructors are proofs: Value.litInt 42 proves that .litInt 42 is a value.

Shifting and substitution

De Bruijn indices require two operations that named variables don’t.

Shifting (shift d c e): when we move a term under a new binder, its free variables need to be incremented so they still point to the right place. The cutoff c tracks how many binders we’ve entered, so bound variables (below c) are left alone:

Before shift:    (λ int (var 0) (var 1))
                              ↑          ↑
                          bound (0)   free (1)

After shift 1 0: (λ int (var 0) (var 2))
                              ↑          ↑
                        still bound   free, shifted up

Substitution (subst j s e): replace variable j with term s, and decrement variables above j (since the binder that introduced variable j has been consumed by β-reduction). Under a binder, j increments and s gets shifted:

def shift (d : Nat) (c : Nat) : Expr → Expr
  | .var k      => if k < c then .var k else .var (k + d)
  | .litInt n   => .litInt n
  | .litBool b  => .litBool b
  | .lam τ body => .lam τ (shift d (c + 1) body)
  | .app e₁ e₂  => .app (shift d c e₁) (shift d c e₂)
  | .add e₁ e₂  => .add (shift d c e₁) (shift d c e₂)
  | .neg e      => .neg (shift d c e)
  | .ifz e₁ e₂ e₃ => .ifz (shift d c e₁) (shift d c e₂) (shift d c e₃)
  | .letE e₁ e₂ => .letE (shift d c e₁) (shift d (c + 1) e₂)

def subst (j : Nat) (s : Expr) : Expr → Expr
  | .var k      => if k == j then s
                    else if j < k then .var (k - 1)
                    else .var k
  | .litInt n   => .litInt n
  | .litBool b  => .litBool b
  | .lam τ body => .lam τ (subst (j + 1) (shift 1 0 s) body)
  | .app e₁ e₂  => .app (subst j s e₁) (subst j s e₂)
  | .add e₁ e₂  => .add (subst j s e₁) (subst j s e₂)
  | .neg e      => .neg (subst j s e)
  | .ifz e₁ e₂ e₃ => .ifz (subst j s e₁) (subst j s e₂) (subst j s e₃)
  | .letE e₁ e₂ => .letE (subst j s e₁) (subst (j + 1) (shift 1 0 s) e₂)

Notice how subst under a lam increments j (the variable being replaced is one deeper) and shifts s (so its free variables still refer to the right things). This is the standard TAPL Chapter 6 formulation.

Typing contexts

A context maps de Bruijn indices to types. We represent it as a function Nat → Option Ty: position 0 is the most recent binder. extend pushes a new type at position 0. insertAt inserts at an arbitrary position (needed for the weakening lemma).

abbrev Ctx := Nat → Option Ty

def Ctx.empty : Ctx := fun _ => none

def Ctx.extend (Γ : Ctx) (τ : Ty) : Ctx
  | 0     => some τ
  | n + 1 => Γ n

def Ctx.insertAt (Γ : Ctx) (c : Nat) (τ : Ty) : Ctx :=
  fun n => if n < c then Γ n
           else if n = c then some τ
           else Γ (n - 1)

Using a function (rather than a list) makes context operations simple and avoids all list-index arithmetic.

Small-step semantics

Each constructor of Step is one evaluation rule. Here are the key rules side by side. The + in E-AddN is metalanguage integer addition (computing the result), not the object-language add form.

Congruence rules (stepping inside a compound expression):

Rule
Lean4 
| appL (e₁ e₁' e₂ : Expr)
  : Step e₁ e₁'
  → Step (.app e₁ e₂) (.app e₁' e₂)
Rule
Lean4 
| appR (v₁ e₂ e₂' : Expr)
  : Value v₁ → Step e₂ e₂'
  → Step (.app v₁ e₂) (.app v₁ e₂')

Plus analogous congruence rules for add, neg, if0, and let (same pattern: step one subexpression, leave the rest unchanged).

The full Step inductive in Lean4:

inductive Step : Expr → Expr → Prop where
  | appL    (e₁ e₁' e₂ : Expr)
    : Step e₁ e₁' → Step (.app e₁ e₂) (.app e₁' e₂)
  | appR    (v₁ e₂ e₂' : Expr)
    : Value v₁ → Step e₂ e₂' → Step (.app v₁ e₂) (.app v₁ e₂')
  | appAbs  (τ : Ty) (body v₂ : Expr)
    : Value v₂ → Step (.app (.lam τ body) v₂) (subst 0 v₂ body)
  | addL    (e₁ e₁' e₂ : Expr)
    : Step e₁ e₁' → Step (.add e₁ e₂) (.add e₁' e₂)
  | addR    (v₁ e₂ e₂' : Expr)
    : Value v₁ → Step e₂ e₂' → Step (.add v₁ e₂) (.add v₁ e₂')
  | addN    (n₁ n₂ : Int)
    : Step (.add (.litInt n₁) (.litInt n₂)) (.litInt (n₁ + n₂))
  | negStep (e e' : Expr)
    : Step e e' → Step (.neg e) (.neg e')
  | negN    (n : Int)
    : Step (.neg (.litInt n)) (.litInt (-n))
  | ifStep  (e₁ e₁' e₂ e₃ : Expr)
    : Step e₁ e₁' → Step (.ifz e₁ e₂ e₃) (.ifz e₁' e₂ e₃)
  | ifTrue  (e₂ e₃ : Expr)
    : Step (.ifz (.litInt 0) e₂ e₃) e₂
  | ifFalse (n : Int) (e₂ e₃ : Expr)
    : n ≠ 0 → Step (.ifz (.litInt n) e₂ e₃) e₃
  | letStep (e₁ e₁' e₂ : Expr)
    : Step e₁ e₁' → Step (.letE e₁ e₂) (.letE e₁' e₂)
  | letVal  (v₁ e₂ : Expr)
    : Value v₁ → Step (.letE v₁ e₂) (subst 0 v₁ e₂)

The pattern: congruence rules (appL, appR, addL, etc.) step inside a compound expression. Computation rules (appAbs, addN, ifTrue, etc.) do the actual work when all operands are values.

Canonical Forms

Before we tackle the main theorems, we need a small observation that will come up repeatedly. Think about what happens when we know something is a value with a specific type. There are only three kinds of values: integer literals, boolean literals, and lambdas. And each one can only have certain types:

  • An integer literal like 42 can only have type int (by T-Int).
  • A boolean literal can only have type bool (by T-Bool).
  • A lambda can only have an arrow type τ₁ → τ₂ (by T-Lam).

The canonical forms lemma just makes this official: if you know both the type and that something is a value, you know its exact shape.

Why do we care? Imagine you’re trying to prove progress for (e₁ e₂). You’ve established (via the IH) that e₁ is a value with type τ₁ → τ₂. You want to use E-AppAbs, but that rule requires e₁ to literally be (λ (x:τ₁) body). Canonical forms bridges the gap: “value with arrow type” implies “is a lambda.”

The proof is by cases on the value. Each impossible combination (e.g., litBool with type int) is a contradiction, which Lean resolves automatically with cases ht:

theorem canonical_int {Γ : Ctx} {e : Expr}
    (ht : HasType Γ e .int) (hv : Value e) :
    ∃ n : Int, e = .litInt n := by
  cases hv with
  | litInt n       => exact ⟨n, rfl⟩
  | litBool b      => cases ht
  | lam τ body     => cases ht

theorem canonical_bool {Γ : Ctx} {e : Expr}
    (ht : HasType Γ e .bool) (hv : Value e) :
    ∃ b : Bool, e = .litBool b := by
  cases hv with
  | litBool b      => exact ⟨b, rfl⟩
  | litInt n       => cases ht
  | lam τ body     => cases ht

theorem canonical_arrow {Γ : Ctx} {e : Expr} {τ₁ τ₂ : Ty}
    (ht : HasType Γ e (τ₁ ⇒ τ₂)) (hv : Value e) :
    ∃ body : Expr, e = .lam τ₁ body := by
  cases hv with
  | lam τ body =>
    cases ht with
    | tLam => exact ⟨body, rfl⟩
  | litInt n       => cases ht
  | litBool b      => cases ht

The ⟨n, rfl⟩ syntax is Lean’s way of providing an existential witness: “the witness is n, and the proof of equality is reflexivity.” The cases ht tactic asks Lean to find a typing rule that could assign the given type to the given value form; when none exists, the case is impossible and Lean closes it.

Progress

Theorem. If HasType Ctx.empty e τ (well-typed, closed), then either e is a value or there exists e' such that Step e e'.

How would you approach this proof?

The first question: what do we induct on? We have a well-typed expression e, so our options are: induction on e (the expression structure), or induction on the typing derivation (the proof that e has type τ). Let’s think about what each gives us.

If we induct on e, we’d case-split on whether e is a variable, a literal, a lambda, an application, etc. For a literal, we’re done (it’s a value). For an application (e₁ e₂), we’d know by IH that e₁ and e₂ satisfy progress… but wait, we only know they satisfy progress if they’re well-typed. The IH from structural induction on e doesn’t give us that. We’d have to extract the subderivations from the typing proof, which is awkward.

Induction on the typing derivation is cleaner. Each case of the induction corresponds to a typing rule (T-Int, T-App, T-Lam, etc.), and the IH gives us progress for the premises of that rule. For T-App, the IH directly says “e₁ satisfies progress” and “e₂ satisfies progress,” which is exactly what we need.

Lesson: when your theorem’s hypothesis is a derivation (like a typing proof), induct on the derivation.

Walking through a concrete example

Consider ((λ (x : int) x) 5) : int. Its typing derivation is:

The progress proof walks this tree bottom-up. We’re at the root, T-App, so we need to show the application can step. The IH tells us about the two children:

  • Left child (λ (x : int) x): typed by T-Lam, which is a value (lambdas are values). IH says: “it’s a value.” Good.
  • Right child 5: typed by T-Int, which is a value (literals are values). IH says: “it’s a value.” Good.

Both are values. Now what? We know e₁ has type int → int and is a value. By canonical forms, it must be a lambda. So e₁ = (λ τ body) for some body. Now E-AppAbs applies: ((λ τ body) 5) → subst 0 5 body. We found our step.

Now consider a different example: ((+ 3 5) 7). This is typed by T-App, where the left child is (+ 3 5) typed by T-Add. The IH on the left child says: both 3 and 5 are values (by T-Int), both are integers (by canonical forms), so E-AddN fires and (+ 3 5) → 8. Since the left child can step, E-AppL fires: ((+ 3 5) 7) → (8 7). We didn’t even need to look at the right child.

This is the general pattern for all compound cases:

  1. Ask the IH about each subexpression.
  2. If any subexpression can step, use the corresponding congruence rule (E-AppL, E-AppR, E-AddL, etc.).
  3. If all subexpressions are values, use canonical forms to determine their shapes, then identify the computation rule.

The proof, case by case

Values (T-Int, T-Bool, T-Lam): These are already values. Done immediately.

Variables (T-Var): The term is closed (empty context), so no variable can be in scope. The context lookup Γ i = some τ is impossible when Γ = Ctx.empty. Contradiction.

Application (T-App): The interesting case. We have ⊢ (e₁ e₂) : τ₂ with ⊢ e₁ : τ₁ → τ₂ and ⊢ e₂ : τ₁. The IH gives us progress for both children. Three subcases:

  • e₁ can step → use E-AppL: (e₁ e₂) → (e₁' e₂)
  • e₁ is a value, e₂ can step → use E-AppR: (v₁ e₂) → (v₁ e₂')
  • Both values → canonical forms on e₁ gives us a lambda → E-AppAbs

Addition (T-Add): Same pattern. If either operand steps, use E-AddL or E-AddR. If both are values, canonical forms gives us integer literals, so E-AddN fires.

Conditional (T-If): The condition e₁ has type int. If it steps, use E-IfStep. If it’s a value, canonical forms gives us an integer n. Then we decide: if n = 0, use E-IfTrue; otherwise E-IfFalse.

Let (T-Let): Simplest compound case. If e₁ steps, E-LetStep. If e₁ is a value, E-LetVal.

The full Lean4 proof

private theorem progress_aux (Γ : Ctx) (e : Expr) (τ : Ty)
    (ht : HasType Γ e τ) (hΓ : Γ = Ctx.empty) :
    Value e ∨ ∃ e' : Expr, Step e e' := by
  induction ht with
  | tInt  => left; exact Value.litInt _
  | tBool => left; exact Value.litBool _
  | tVar _ i _ h => subst hΓ; simp [Ctx.empty] at h
  | tLam => left; exact Value.lam _ _
  | tApp _ e₁ e₂ τ₁ τ₂ ht₁ ht₂ ih₁ ih₂ =>
    right
    rcases ih₁ hΓ with hv₁ | ⟨e₁', hs₁⟩
    · rcases ih₂ hΓ with hv₂ | ⟨e₂', hs₂⟩
      · obtain ⟨body, rfl⟩ := canonical_arrow ht₁ hv₁
        exact ⟨_, Step.appAbs _ _ _ hv₂⟩
      · exact ⟨_, Step.appR _ _ _ hv₁ hs₂⟩
    · exact ⟨_, Step.appL _ _ _ hs₁⟩
  | tAdd _ e₁ e₂ ht₁ ht₂ ih₁ ih₂ =>
    right
    rcases ih₁ hΓ with hv₁ | ⟨e₁', hs₁⟩
    · rcases ih₂ hΓ with hv₂ | ⟨e₂', hs₂⟩
      · obtain ⟨n₁, rfl⟩ := canonical_int ht₁ hv₁
        obtain ⟨n₂, rfl⟩ := canonical_int ht₂ hv₂
        exact ⟨_, Step.addN _ _⟩
      · exact ⟨_, Step.addR _ _ _ hv₁ hs₂⟩
    · exact ⟨_, Step.addL _ _ _ hs₁⟩
  | tNeg _ e ht ih =>
    right
    rcases ih hΓ with hv | ⟨e', hs⟩
    · obtain ⟨n, rfl⟩ := canonical_int ht hv
      exact ⟨_, Step.negN _⟩
    · exact ⟨_, Step.negStep _ _ hs⟩
  | tIf _ e₁ e₂ e₃ τ ht₁ _ _ ih₁ _ _ =>
    right
    rcases ih₁ hΓ with hv₁ | ⟨e₁', hs₁⟩
    · obtain ⟨n, rfl⟩ := canonical_int ht₁ hv₁
      by_cases h : n = 0
      · subst h; exact ⟨_, Step.ifTrue _ _⟩
      · exact ⟨_, Step.ifFalse _ _ _ h⟩
    · exact ⟨_, Step.ifStep _ _ _ _ hs₁⟩
  | tLet _ e₁ e₂ τ₁ τ₂ _ _ ih₁ _ =>
    right
    rcases ih₁ hΓ with hv₁ | ⟨e₁', hs₁⟩
    · exact ⟨_, Step.letVal _ _ hv₁⟩
    · exact ⟨_, Step.letStep _ _ _ hs₁⟩

theorem progress {e : Expr} {τ : Ty} (ht : HasType Ctx.empty e τ) :
    Value e ∨ ∃ e' : Expr, Step e e' :=
  progress_aux Ctx.empty e τ ht rfl

Reading the proof case by case:

  • tInt/tBool/tLam: already a value. left picks the first disjunct.
  • tVar: subst hΓ replaces the context with Ctx.empty, then simp [Ctx.empty] at h shows the lookup h is impossible (empty context maps everything to none).
  • tApp: right says we’ll find a step. rcases ih₁ hΓ splits the IH on e₁ into “value” or “steps.” If e₁ steps, use appL. If e₁ is a value, split the IH on e₂. If both are values, canonical_arrow tells us e₁ is a lambda, so appAbs fires.
  • tAdd: same pattern, but canonical_int extracts literal integers, so addN fires.
  • tIf: after canonical forms gives us an integer, by_cases h : n = 0 decides which branch.
  • tLet: simplest compound case: if e₁ is a value, letVal; if it steps, letStep.

The Substitution Lemma

This is the hardest proof in the development, and the most important one to understand deeply. Let’s build it from scratch, starting with why we need it and discovering the complications as we go.

Why we need this lemma

When β-reduction fires, (λ body) v → body[0 := v], we need to know the result is still well-typed. We have:

  • Γ.extend τ₁ ⊢ body : τ₂ (the body is typed with variable 0 bound to τ₁)
  • Γ ⊢ v : τ₁ (the argument has the right type)

We need: Γ ⊢ body[0 := v] : τ₂. Intuitively this should work: every place body used variable 0, it expected a τ₁, and v is a τ₁. But “intuitively should work” isn’t a proof. Let’s try.

First attempt: induction at position 0

We try to prove: if Γ.extend τ₁ ⊢ e : τ₂ and Γ ⊢ v : τ₁, then Γ ⊢ subst 0 v e : τ₂. We induct on the typing derivation of e.

T-Var case, variable is 0: The substitution replaces variable 0 with v. We need Γ ⊢ v : τ₁. That’s exactly our hypothesis.

T-Var case, variable is i > 0: The substitution decrements i to i-1. We need Γ (i-1) = some τ. Since the original lookup was (Γ.extend τ₁) i = some τ, and i > 0, this is Γ (i-1). Works.

T-App case: Structural, apply IH to both subexpressions. Fine.

T-Lam case: here’s where we get stuck. We have a nested lambda: (λ σ body') typed under Γ.extend τ₁. The premise is:

(Γ.extend τ₁).extend σ ⊢ body' : τ₂'

After substitution, subst 0 v (λ σ body') becomes λ σ (subst 1 (shift 1 0 v) body'). So we need:

Γ.extend σ ⊢ subst 1 (shift 1 0 v) body' : τ₂'

But our IH only talks about substitution at position 0! We need position 1 here. The IH doesn’t apply.

The fix: generalize over the position

The failed attempt reveals what we need: a lemma that works at any substitution position j, not just 0. Under each binder, j increments. The generalized statement:

If Γ.insertAt j τ₁ ⊢ e : τ₂ and Γ ⊢ v : τ₁, then Γ ⊢ subst j v e : τ₂.

Now in the T-Lam case, the IH gives us substitution at position j+1, which is exactly what we need after going under the binder.

But we hit another wall: weakening

In the T-Lam case with the generalized lemma, we have Γ ⊢ v : τ₁ and we need Γ.extend σ ⊢ shift 1 0 v : τ₁ (because v gets shifted when it goes under the new binder). This is a weakening lemma: adding a type to the context (and shifting accordingly) preserves typing.

Weakening is itself proved by induction on the typing derivation. The interesting case is T-Lam, which uses a commutation lemma: extending a context and then inserting at position c is the same as inserting at position c+1 and then extending. This is the key piece of de Bruijn bookkeeping.

So the full dependency chain is:

commutation (extend_insertAt)
    ↓
weakening
    ↓
substitution (generalized)
    ↓
substitution (at position 0)

Each lemma was discovered by getting stuck in the proof of the next one. This is typical of formalization: the proof attempt itself tells you what lemmas you need.

Lean4 code: building up the infrastructure

Context helper lemmas (properties of insertAt):

These are the basic facts about inserting into a context. They say: looking up the inserted position gives the inserted type; below is unchanged; above is shifted down. We’ll use these throughout.

theorem Ctx.insertAt_self (Γ : Ctx) (j : Nat) (σ : Ty) :
    (Γ.insertAt j σ) j = some σ := by
  simp [Ctx.insertAt]

theorem Ctx.insertAt_lt (Γ : Ctx) (j i : Nat) (σ : Ty) (h : i < j) :
    (Γ.insertAt j σ) i = Γ i := by
  simp [Ctx.insertAt, h]

theorem Ctx.insertAt_gt (Γ : Ctx) (j i : Nat) (σ : Ty) (h : j < i) :
    (Γ.insertAt j σ) i = Γ (i - 1) := by
  unfold Ctx.insertAt
  have h1 : ¬(i < j) := by omega
  have h2 : ¬(i = j) := by omega
  rw [if_neg h1, if_neg h2]

theorem Ctx.insertAt_zero (Γ : Ctx) (σ : Ty) :
    Γ.insertAt 0 σ = Γ.extend σ := by
  funext n; simp [Ctx.insertAt, Ctx.extend]; cases n <;> simp

Weakening (the lemma we discovered was needed in the T-Lam case):

The key case is T-Lam, which uses the commutation lemma extend_insertAt. The rest are structural.

theorem weakening {Γ : Ctx} {e : Expr} {τ σ : Ty} {c : Nat}
    (ht : HasType Γ e τ) :
    HasType (Γ.insertAt c σ) (shift 1 c e) τ := by
  induction ht generalizing c with
  | tInt _ n => simp [shift]; exact HasType.tInt _ _
  | tBool _ b => simp [shift]; exact HasType.tBool _ _
  | tVar _ i τ hlookup =>
    simp only [shift]
    split
    · next hlt =>
      exact HasType.tVar _ _ _
        (by rw [Ctx.insertAt_lt _ c _ σ hlt]; exact hlookup)
    · next hge =>
      have hge' : c ≤ i := Nat.le_of_not_lt hge
      have hgt : c < i + 1 := by omega
      apply HasType.tVar
      rw [Ctx.insertAt_gt _ c _ σ hgt]
      have : i + 1 - 1 = i := by omega
      rw [this]; exact hlookup
  | tLam _ τ₁ τ₂ body _ ih =>
    simp [shift]
    apply HasType.tLam
    rw [← Ctx.extend_insertAt]
    exact ih
  | tApp _ e₁ e₂ τ₁ τ₂ _ _ ih₁ ih₂ =>
    simp [shift]; exact HasType.tApp _ _ _ _ _ ih₁ ih₂
  | tAdd _ e₁ e₂ _ _ ih₁ ih₂ =>
    simp [shift]; exact HasType.tAdd _ _ _ ih₁ ih₂
  | tNeg _ e _ ih =>
    simp [shift]; exact HasType.tNeg _ _ ih
  | tIf _ e₁ e₂ e₃ τ _ _ _ ih₁ ih₂ ih₃ =>
    simp [shift]; exact HasType.tIf _ _ _ _ _ ih₁ ih₂ ih₃
  | tLet _ e₁ e₂ τ₁ τ₂ _ _ ih₁ ih₂ =>
    simp [shift]
    apply HasType.tLet _ _ _ _ _
    · exact ih₁
    · rw [← Ctx.extend_insertAt]; exact ih₂

The T-Var case splits on whether the variable is below or above the insertion point. The T-Lam case uses Ctx.extend_insertAt: extending a context and then inserting is the same as inserting and then extending (with the position shifted). This commutation lemma is the key piece of de Bruijn bookkeeping.

Generalized substitution (at arbitrary position j):

private theorem subst_aux (Γ₀ : Ctx) (e : Expr) (τ₂ : Ty)
    (he : HasType Γ₀ e τ₂)
    (Γ : Ctx) (v : Expr) (τ₁ : Ty) (j : Nat)
    (hΓ : Γ₀ = Γ.insertAt j τ₁) (hv : HasType Γ v τ₁) :
    HasType Γ (subst j v e) τ₂ := by
  induction he generalizing Γ j v τ₁ with
  | tInt => subst hΓ; simp [subst]; exact HasType.tInt _ _
  | tBool => subst hΓ; simp [subst]; exact HasType.tBool _ _
  | tVar _ i τ hlookup =>
    subst hΓ; simp [subst]
    split
    · next heq =>
      have hij : i = j := by omega
      subst hij
      rw [Ctx.insertAt_self] at hlookup
      injection hlookup with h; subst h; exact hv
    · split
      · next hne hjlt =>
        have hij : j < i := by omega
        rw [Ctx.insertAt_gt _ _ _ _ hij] at hlookup
        exact HasType.tVar _ _ _ hlookup
      · next hne hjge =>
        have hij : i < j := by omega
        rw [Ctx.insertAt_lt _ _ _ _ hij] at hlookup
        exact HasType.tVar _ _ _ hlookup
  | tLam _ τ₁' τ₂' body _ ih =>
    subst hΓ; simp [subst]
    apply HasType.tLam
    apply ih
    · exact (Ctx.extend_insertAt Γ τ₁' τ₁ j).symm
    · have h := @weakening Γ _ _ τ₁' 0 hv
      rwa [Ctx.insertAt_zero] at h
  | tApp _ e₁ e₂ σ₁ σ₂ _ _ ih₁ ih₂ =>
    subst hΓ; simp [subst]
    exact HasType.tApp _ _ _ _ _ (ih₁ _ _ _ _ rfl hv) (ih₂ _ _ _ _ rfl hv)
  | tAdd _ e₁ e₂ _ _ ih₁ ih₂ =>
    subst hΓ; simp [subst]
    exact HasType.tAdd _ _ _ (ih₁ _ _ _ _ rfl hv) (ih₂ _ _ _ _ rfl hv)
  | tNeg _ e _ ih =>
    subst hΓ; simp [subst]
    exact HasType.tNeg _ _ (ih _ _ _ _ rfl hv)
  | tIf _ e₁ e₂ e₃ τ _ _ _ ih₁ ih₂ ih₃ =>
    subst hΓ; simp [subst]
    exact HasType.tIf _ _ _ _ _
      (ih₁ _ _ _ _ rfl hv) (ih₂ _ _ _ _ rfl hv) (ih₃ _ _ _ _ rfl hv)
  | tLet _ e₁ e₂ σ₁ σ₂ _ _ ih₁ ih₂ =>
    subst hΓ; simp [subst]
    apply HasType.tLet _ _ _ _ _
    · exact ih₁ _ _ _ _ rfl hv
    · apply ih₂
      · exact (Ctx.extend_insertAt Γ σ₁ τ₁ j).symm
      · have h := @weakening Γ _ _ σ₁ 0 hv
        rwa [Ctx.insertAt_zero] at h

Reading the key cases:

  • tVar (i = j): the variable being substituted. insertAt_self tells us the looked-up type is τ₁. Since the substitution replaces it with v, and v has type τ₁, we’re done.
  • tVar (i > j): above the substitution point. The index decrements by one (since a binder was consumed). insertAt_gt aligns the context lookup.
  • tVar (i < j): below the substitution point. Unchanged. insertAt_lt aligns.
  • tLam: the induction increments j and shifts v. We need the commutation lemma (extend_insertAt) to align the context, and weakening at position 0 to give v the right type under the extended context.
  • All other cases: structural. Apply IH to each subexpression, passing rfl for the context equation and hv for the value typing.

The public API wraps this at position 0:

theorem substitution_general {Γ : Ctx} {e v : Expr} {τ₁ τ₂ : Ty}
    {j : Nat}
    (he : HasType (Γ.insertAt j τ₁) e τ₂) (hv : HasType Γ v τ₁) :
    HasType Γ (subst j v e) τ₂ :=
  subst_aux _ _ _ he _ _ _ _ rfl hv

theorem substitution {Γ : Ctx} {e v : Expr} {τ₁ τ₂ : Ty}
    (he : HasType (Γ.extend τ₁) e τ₂)
    (hv : HasType Γ v τ₁) :
    HasType Γ (subst 0 v e) τ₂ := by
  rw [Ctx.extend_eq_insertAt] at he
  exact substitution_general he hv

Preservation

Theorem. If HasType Γ e τ and Step e e', then HasType Γ e' τ.

How would you approach this proof?

Again, what do we induct on? We have two things: a typing derivation ht : HasType Γ e τ and a step hs : Step e e'. We could try induction on hs (the step), but then we’d need to extract typing information for the subexpressions, which is awkward. Induction on ht (the typing) works better: each case tells us the shape of e, and then we do case analysis on which step rule could have fired.

Most cases fall into two patterns:

Congruence cases (e.g., T-App + E-AppL): a subexpression stepped. The IH says it preserved its type. Rebuild the typing derivation with the new subexpression. This is mechanical.

Computation cases (e.g., T-App + E-AppAbs): the real work. β-reduction produces subst 0 v₂ body. We need to show this is well-typed. This is exactly what the substitution lemma says. The entire substitution infrastructure we just built exists for this single moment.

Walking through β-reduction concretely

Take ((λ (x : int) (+ x 1)) 5) → (+ 5 1). The typing derivation before the step:

E-AppAbs fires. From the derivation, we extract:

  • x : int ⊢ (+ x 1) : int (the body is well-typed assuming x is int)
  • ⊢ 5 : int (the argument is an int)

The substitution lemma says: since the body is typed under Γ.extend int and 5 has type int under Γ, then subst 0 5 (+ x 1) (which is (+ 5 1)) has type int under Γ. That’s preservation for this step.

The substitution lemma constructed this derivation for us: it walked through the body (+ x 1), replaced the T-Var node for x with the T-Int proof for 5, and rebuilt the T-Add on top.

The full Lean4 proof

private theorem preservation_general {Γ : Ctx} {e e' : Expr} {τ : Ty}
    (ht : HasType Γ e τ) (hs : Step e e') :
    HasType Γ e' τ := by
  induction ht generalizing e' with
  | tInt => cases hs
  | tBool => cases hs
  | tVar => cases hs
  | tLam => cases hs
  | tApp Γ e₁ e₂ τ₁ τ₂ ht₁ ht₂ ih₁ ih₂ =>
    cases hs with
    | appL _ e₁' _ hs₁ =>
      exact HasType.tApp _ _ _ _ _ (ih₁ hs₁) ht₂
    | appR _ _ e₂' _ hs₂ =>
      exact HasType.tApp _ _ _ _ _ ht₁ (ih₂ hs₂)
    | appAbs _ body _ hv₂ =>
      cases ht₁ with
      | tLam _ _ _ _ htbody => exact substitution htbody ht₂
  | tAdd Γ e₁ e₂ ht₁ ht₂ ih₁ ih₂ =>
    cases hs with
    | addL _ e₁' _ hs₁ =>
      exact HasType.tAdd _ _ _ (ih₁ hs₁) ht₂
    | addR _ _ e₂' _ hs₂ =>
      exact HasType.tAdd _ _ _ ht₁ (ih₂ hs₂)
    | addN => exact HasType.tInt _ _
  | tNeg Γ e ht ih =>
    cases hs with
    | negStep _ e' hs' => exact HasType.tNeg _ _ (ih hs')
    | negN => exact HasType.tInt _ _
  | tIf Γ e₁ e₂ e₃ τ ht₁ ht₂ ht₃ ih₁ _ _ =>
    cases hs with
    | ifStep _ e₁' _ _ hs₁ =>
      exact HasType.tIf _ _ _ _ _ (ih₁ hs₁) ht₂ ht₃
    | ifTrue => exact ht₂
    | ifFalse => exact ht₃
  | tLet Γ e₁ e₂ τ₁ τ₂ ht₁ ht₂ ih₁ _ =>
    cases hs with
    | letStep _ e₁' _ hs₁ =>
      exact HasType.tLet _ _ _ _ _ (ih₁ hs₁) ht₂
    | letVal _ _ hv₁ => exact substitution ht₂ ht₁

theorem preservation {e e' : Expr} {τ : Ty}
    (ht : HasType Ctx.empty e τ) (hs : Step e e') :
    HasType Ctx.empty e' τ :=
  preservation_general ht hs

Reading the key cases:

  • tInt/tBool/tVar/tLam: these forms can never step (cases hs finds no matching step rule), so the cases are vacuously true.
  • tApp + appAbs: this is β-reduction, the critical case. We invert ht₁ to extract htbody : HasType (Γ.extend τ₁) body τ₂, then apply substitution htbody ht₂ to conclude that subst 0 v₂ body has type τ₂.
  • tApp + appL/appR: congruence. The subexpression that stepped preserves its type by IH; rebuild with tApp.
  • tAdd + addN: both operands were integer literals, so the result litInt (n₁ + n₂) has type int by tInt.
  • tIf + ifTrue/ifFalse: the selected branch already has the right type (both branches were required to have type τ by tIf).
  • tLet + letVal: same as β-reduction: apply substitution.

Putting It Together: Type Soundness

With progress and preservation in hand, type soundness follows by iteration:

inductive MultiStep : Expr → Expr → Prop where
  | refl (e : Expr) : MultiStep e e
  | step (e e' e'' : Expr)
    : Step e e' → MultiStep e' e'' → MultiStep e e''

theorem preservation_multi {e e' : Expr} {τ : Ty}
    (ht : HasType Ctx.empty e τ) (hms : MultiStep e e') :
    HasType Ctx.empty e' τ := by
  induction hms with
  | refl => exact ht
  | step _ _ _ hs _ ih => exact ih (preservation ht hs)

theorem type_soundness {e e' : Expr} {τ : Ty}
    (ht : HasType Ctx.empty e τ) (hms : MultiStep e e') :
    Value e' ∨ ∃ e'' : Expr, Step e' e'' :=
  progress (preservation_multi ht hms)

MultiStep is the reflexive-transitive closure of Step. preservation_multi iterates preservation over multiple steps. type_soundness combines them: after any number of steps from a well-typed term, apply progress to the (still well-typed) result.

What this means: if you write a well-typed STLC program, you will never see a runtime type error. Every intermediate state is well-typed, and the program either keeps running or reaches a value. Since STLC has no general recursion (the Y combinator is untypable), every well-typed STLC program terminates and produces a value.
